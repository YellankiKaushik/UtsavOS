# Workspace limits and data lifecycle

FR-020 is partial: the database dashboard and limits work; subscription processing does not. Stripe Marketplace returned `integration_terms_acceptance_required`. No resource, SDK, price, checkout, paid subscription or webhook verification is claimed. `/api/billing/webhook` always returns `503 BILLING_NOT_CONFIGURED` and cannot grant entitlements. Complete the owner integration setup before implementing provider-specific signature verification, event receipts, ordering/reconciliation and checkout; test those in provider test mode before enabling billing.

The synthetic pilot defaults are 100 active events, 20 AI attempts per UTC day including failures, 20 active members and 200 MiB of private originals/reservations pending cleanup. These are safety limits, not a pricing promise. Administrative entitlement rows are private, have bounded values and expiry, and cannot be written by ordinary sessions. Expired/suspended rows fall back to pilot limits. Creation, unarchiving, AI reservation, team acceptance and document reservation enforce limits inside the existing workspace transaction. Event and quota races run on real PostgreSQL. Managers can read their dashboard; other tenants and ordinary members cannot read workspace aggregates. Existing records are retained when a limit falls below current usage.

FR-021 supports owner event JSON exports, guest CSV, existing profile/guest correction forms, eligible event operational erasure, and durable self account deletion review requests. CSV cells neutralize spreadsheet formulas. JSON contains planning, functions, contacts, financial records, AI drafts/proposals and document pages/extractions. Invitation capabilities/hashes are excluded. Originals remain separate private attachment downloads. The synchronous export cap is 3 MB; larger exports need an assisted export process before customer onboarding.

Event deletion is explicit and has two steps. Requesting it increments the version, freezes writes and revokes RSVP capabilities. Any financial commitment, including cancelled history, or a recent started AI request puts the event in retention review. This state cannot erase financial evidence or referenced originals. Eligible requests archive originals; the server removes those using the owner's ordinary Storage session. PostgreSQL checks actual object absence before deleting operational rows. Failed cleanup is retryable and does not mark completion. A completed request retains an opaque event row, membership, account identity, usage and redacted audit metadata; erasure cannot be undone through the application. The event cannot be edited after erasure. Receipts containing old planning snapshots are removed. The same completed erase key replays its saved result.

Account review requests are durable, self scoped, naturally idempotent, cancellable and rate limited. They explicitly never claim Auth deletion or backup removal. A verified operator process, ownership/financial retention review, provider copy handling, backup expiry/restore suppression and published privacy/support policy remain commercial release prerequisites. No jurisdictional compliance or certification is claimed.

Exposure is off by default: `FEATURE_WORKSPACE_DASHBOARD=false`, `FEATURE_DATA_LIFECYCLE=false`. The isolated review branch enables each only after genuine ordinary-session hosted tests. Entitlement and lifecycle database protections remain authoritative independently of UI flags. Production was not promoted.
